# 分层驱动调试方法论

> **Top-Down / Bottom-Up 融合分析与 Hierarchical Driver Debugging**
>
> 解决搜索空间过早收敛问题，建立真正的分层诊断体系

---

## 1. 问题诊断：当前决策树的结构性缺陷

### 1.1 伪分层问题

当前 `command-design.md` 中的"Phase"并非真正的层次抽象，而是执行顺序标签：

```
当前结构 (伪分层):
Phase 1: 资源定界 ──► Phase 2: 模式识别 ──► Phase 3: 热点溯源
    │                      │                      │
    ▼                      ▼                      ▼
check-cpu-bottleneck   cluster-symbols        get-hotspots
show-cpu-usage         cluster-paths          find-callers
analyze-core-distribution count-process-variety
```

**核心问题**：所谓的"分层"只是线性流水线的包装，缺乏层次间的递进关系。

### 1.2 搜索空间过早收敛

Phase 1 "资源定界"仅关注 CPU 维度：

| 检查项 | 覆盖范围 | 缺失维度 |
|--------|----------|----------|
| `check-cpu-bottleneck` | CPU 限制/饱和 | 内存瓶颈、IO 阻塞 |
| `show-cpu-usage` | user/kernel 分解 | 调度延迟、上下文切换 |
| `analyze-core-distribution` | 核心负载分布 | NUMA 影响、缓存亲和性 |

**后果**：如果在 Phase 1 未发现 CPU 异常，诊断路径即中断，无法自动扩展到其他资源维度。

### 1.3 三假说设计的平面化

当前的"代码/架构/环境"三假说是**平铺竞争**，而非**层次驱动**：

```
当前:  代码层 ←──竞争──→ 架构层 ←──竞争──→ 环境层
       (热点函数)        (锁竞争)          (CPU限制)

问题：没有明确哪个是驱动力，哪个是表现
```

### 1.4 Bottom-Up 的形式化

当前 "Phase 3: 热点溯源 (Bottom-up)" 仅指函数级溯源，**非方法论意义上的 Bottom-Up**：

| 层面 | 真正的 Bottom-Up 应该做 | 当前实际 |
|------|------------------------|----------|
| 证据层 | 从原始样本归纳出模式 | 只是排序输出 |
| 语义层 | 从模式推断瓶颈类别 | 规则匹配，非归纳 |
| 验证层 | 用微观证据证伪宏观假设 | 简单对比，无证伪机制 |
| 收敛层 | 竞争性假设的淘汰决策 | 无明确淘汰标准 |

## 2. 方法论基础

### 2.1 真正的 Top-Down 分析

Top-Down 是从抽象到具体的**层次递进**：

```
Level 0: 现象层      ──► "延迟高" (问题定义)
         │
         ▼ (分解)
Level 1: 系统层      ──► 哪个子系统主导? (CPU/Mem/IO/Net)
         │
         ▼ (分解)
Level 2: 组件层      ──► 哪个组件? (进程/服务/模块)
         │
         ▼ (分解)
Level 3: 机制层      ──► 什么机制? (调度/锁/中断/回收)
         │
         ▼ (分解)
Level 4: 代码层      ──► 哪个函数? (热点/调用链)
```

**关键原则**：每层分解必须**同时探索多个分支**，维护竞争性假设。

### 2.2 真正的 Bottom-Up 分析

Bottom-Up 是从具体到抽象的**证据聚合**：

```
样本数据          ──► 原始 perf 事件样本
     │
     ▼ (聚合)
热点函数          ──► 自顶向下/自底向上的耗时排序
     │
     ▼ (聚合)
调用模式          ──► 公共调用路径、火焰图形状
     │
     ▼ (聚合)
语义类别          ──► 锁/调度/内存/中断 占比
     │
     ▼ (聚合)
根因推断          ──► 与 Top-Down 假设的匹配/冲突
```

### 2.3 V 型融合模型

```
                    问题定义
                       │
         ┌─────────────┴─────────────┐
         │                           │
         ▼                           ▼
    [Top-Down]                  [Bottom-Up]
    假设生成                      证据聚合
         │                           │
    系统层假设                      热点函数
         │                           │
    组件层假设                      调用路径
         │                           │
    机制层假设                      语义聚类
         │                           │
         └─────────────┬─────────────┘
                       ▼
              ┌─────────────────┐
              │  假设-证据交汇点  │
              │  (Convergence)   │
              └────────┬────────┘
                       ▼
                  根因确认/回溯
```

## 3. Hierarchical Driver 模型

### 3.1 五层驱动架构

性能问题的驱动力应按以下层次分析，**从外向内、从宏观到微观**：

```
┌─────────────────────────────────────────────────────────────────┐
│ L1: Workload Driver (负载驱动)                                   │
│    ── 外部请求特征: QPS、并发度、Payload 大小、请求模式            │
│    ── 关键问题: 是流量突发导致的，还是常态负载?                   │
├─────────────────────────────────────────────────────────────────┤
│ L2: Resource Driver (资源驱动)                                   │
│    ── 资源瓶颈: CPU、Memory、IO、Network、File Descriptor         │
│    ── 关键问题: 哪个资源首先成为瓶颈?                             │
├─────────────────────────────────────────────────────────────────┤
│ L3: Scheduler Driver (调度驱动)                                  │
│    ── 调度行为: 上下文切换、调度延迟、亲和性、优先级反转           │
│    ── 关键问题: 是"不能并行"还是"不想并行"?                     │
├─────────────────────────────────────────────────────────────────┤
│ L4: Code Driver (代码驱动)                                       │
│    ── 代码特征: 热点函数、锁粒度、算法复杂度、系统调用频率         │
│    ── 关键问题: 代码层面的具体瓶颈是什么?                         │
├─────────────────────────────────────────────────────────────────┤
│ L5: Environment Driver (环境驱动)                                │
│    ── 环境因素: Cgroup 限制、NUMA 配置、内核版本、硬件特性         │
│    ── 关键问题: 环境配置是否限制了性能发挥?                       │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 驱动层次间的逻辑关系

```
                    性能异常现象
                          │
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
       外部输入?    资源瓶颈?      内部机制?
            │             │             │
            ▼             ▼             ▼
      ┌─────────┐   ┌─────────┐   ┌─────────┐
      │L1 Workload│   │L2 Resource│   │L3 Scheduler│
      │  先检查   │   │  先检查   │   │   先检查    │
      └────┬────┘   └────┬────┘   └────┬────┘
           │             │             │
           ▼             ▼             ▼
      如果 QPS 低    如果 CPU 低    如果调度高
      但延迟高 ──►  但 IO 高   ──►  但用户态低
           │             │             │
           ▼             ▼             ▼
      可能是 L4     可能是 L3     可能是 L4
      代码问题      或 L4 问题     或 L5 问题
           │             │             │
           └─────────────┴─────────────┘
                         │
                         ▼
                    ┌─────────┐
                    │L5 Env   │
                    │排除配置  │
                    │问题      │
                    └─────────┘
```

### 3.3 层次间的证据关联

| 上层证据 | 关联下层 | 诊断含义 |
|----------|----------|----------|
| L1: QPS 正常，延迟升高 | L2: CPU 正常 → L3: 调度高 | 可能是锁竞争导致的"不想并行" |
| L2: CPU 满载，QPS 低 | L4: 单热点函数自耗时高 | 可能是算法复杂度高导致的"不能并行" |
| L3: 不均衡严重 | L5: 亲和性配置 → L4: 线程绑定 | 可能是线程绑定配置错误 |
| L4: 锁函数高 | L3: 调度延迟 → L2: 上下文切换 | 确认是锁竞争而非 CPU 瓶颈 |

## 4. 搜索空间管理：发散-收敛机制

### 4.1 避免搜索空间过小的设计原则

**禁止的行为**：
- ❌ 单维度检查后过早收敛
- ❌ 线性执行顺序替代并行假设
- ❌ 单一路径深入而无回溯机制

**强制的行为**：
- ✅ 每层必须同时维护 ≥3 条竞争性假设
- ✅ 每层的"发散"必须覆盖该层所有可能维度
- ✅ 必须定义明确的"交汇检查点"才允许收敛

### 4.2 分层发散-收敛架构

```
Level 0: 现象层 ──────────────────────────────────────────────
          │
          ▼ 发散 (必须同时启动)
    ┌─────────┬─────────┬─────────┐
    │ 系统维度 │ 负载维度 │ 时序维度 │
    └────┬────┴────┬────┴────┬────┘
         │         │         │
         ▼         ▼         ▼
    ┌─────────────────────────────────┐
    │ 交汇检查点 #1: 确定主导驱动层     │
    │ "系统层证据最强 → 进入 L2 发散"   │
    └────────────────┬────────────────┘
                     │
Level 1: 系统层 ─────┘ 发散 (必须并行检查)
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
    ┌───────┐   ┌───────┐   ┌───────┐
    │  CPU  │   │  Mem  │   │  IO   │
    │ 检查  │   │ 检查  │   │ 检查  │
    └───┬───┘   └───┬───┘   └───┬───┘
        │           │           │
        └───────────┼───────────┘
                    ▼
        ┌───────────────────────┐
        │ 交汇检查点 #2: 资源瓶颈定界 │
        │ "CPU 是主瓶颈 → 进入 L2 CPU" │
        └───────────┬───────────┘
                    │
Level 2: CPU 子系统 ─┘ 发散
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
    ┌───────┐  ┌───────┐  ┌───────┐
    │ 利用率 │  │ 均衡性 │  │ 饱和度 │
    │ 分析  │  │ 分析  │  │ 分析  │
    └───┬───┘  └───┬───┘  └───┬───┘
        │          │          │
        └──────────┼──────────┘
                   ▼
        ┌───────────────────────┐
        │ 交汇检查点 #3: CPU 模式确认  │
        │ "单核满载 → 可能是 L3 调度或 L4 代码" │
        └───────────┬───────────┘
                    │
Level 3-4: 组件/代码层 ─┘ (Bottom-Up 验证)
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
    Top-Down 假设         Bottom-Up 证据
        │                       │
        ▼                       ▼
    "L3 调度问题"    ←──对比──   调度函数占比
    "L4 锁竞争"      ←──对比──   锁函数调用链
    "L4 热点代码"    ←──对比──   自耗时排序
        │                       │
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐
        │ 交汇检查点 #4: 根因确认   │
        │ 假设与证据一致 → 确认根因   │
        │ 假设与证据冲突 → 回溯到 L2   │
        └───────────────────────┘
```

### 4.3 每层的最小发散集

| 层级 | 必须并行检查的维度 | 收敛条件 |
|------|-------------------|----------|
| L0 现象 | 系统/负载/时序 | 确定主导驱动层 |
| L1 系统 | CPU/Mem/IO/Net | 确定瓶颈资源 |
| L2 资源 | 利用率/饱和度/均衡性 | 确定资源模式 |
| L3 组件 | 进程/线程/锁/调度 | 确定组件级瓶颈 |
| L4 代码 | 热点/调用链/语义 | 确定根因函数 |

## 5. 假设-证据交汇检查点

### 5.1 交汇检查点的定义

交汇检查点是 Top-Down 假设与 Bottom-Up 证据进行**一致性验证**的决策节点。

**必须满足的条件才允许通过**：
1. 至少有两条独立的 Bottom-Up 证据支持 Top-Down 假设
2. 无直接矛盾的 Bottom-Up 证据
3. 竞争性假设的证据强度明显较弱

### 5.2 交汇检查点设计

```
┌─────────────────────────────────────────────────────────────┐
│                    交汇检查点模板                            │
├─────────────────────────────────────────────────────────────┤
│ 检查点编号: CP-{Level}-{Sequence}                           │
│ 所在层级: L{X}                                              │
│                                                             │
│ Top-Down 假设:                                              │
│   - 主假设: [描述]                                          │
│   - 竞争性假设: [至少2个]                                    │
│                                                             │
│ Bottom-Up 证据收集:                                         │
│   ┌─────────────┬─────────────┬─────────────┐              │
│   │ 证据来源     │ 证据内容     │ 支持假设    │              │
│   ├─────────────┼─────────────┼─────────────┤              │
│   │ {tool_1}    │ {result}    │ 主/竞争/无关 │              │
│   │ {tool_2}    │ {result}    │ 主/竞争/无关 │              │
│   │ {tool_3}    │ {result}    │ 主/竞争/无关 │              │
│   └─────────────┴─────────────┴─────────────┘              │
│                                                             │
│ 一致性判断:                                                 │
│   [ ] 确认通过  → 进入下一层                                 │
│   [ ] 证据冲突  → 回溯到上层重新发散                         │
│   [ ] 假设存疑  → 补充证据后再判断                           │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 关键交汇检查点示例

#### CP-1-1: L1 系统层定界

| Top-Down 假设 | Bottom-Up 证据 | 一致性判断 |
|--------------|----------------|-----------|
| H1: CPU 瓶颈主导 | `show-cpu-usage` user%+sys% > 80% | ✓ 支持 |
| H2: IO 瓶颈主导 | `show-cpu-usage` iowait% > 20% | ? 待确认 |
| H3: Mem 瓶颈主导 | `cluster-symbols` MEM_RECLAIM 高 | ✗ 不支持 |

**决策**: 如果 H1 有 ≥2 个证据支持，H2/H3 证据不足，则进入 L2 CPU 分析。

#### CP-2-1: L2 CPU 模式识别

| Top-Down 假设 | Bottom-Up 证据 | 一致性判断 |
|--------------|----------------|-----------|
| H1: 单核饱和 | `analyze-core-distribution` 不均衡比率 > 10 | ✓ 支持 |
| H2: 全局饱和 | `check-cpu-bottleneck` 全局利用率 > 80% | ? 部分支持 |
| H3: CPU 限制 | `check-cpu-bottleneck` 检测 cgroup 限制 | ✗ 不支持 |

**决策**: 如果单核饱和证据明确，进入 L3 调度层分析"不能并行" vs "不想并行"。

#### CP-3-1: L3 调度问题定界

| Top-Down 假设 | Bottom-Up 证据 | 一致性判断 |
|--------------|----------------|-----------|
| H1: 锁竞争导致 | `cluster-symbols` LOCK_CONTENTION 高 | ✓ 支持 |
| H2: 调度延迟 | `cluster-symbols` SCHEDULER 高 | ✗ 不支持 |
| H3: 主动休眠 | `find-callers schedule` 显示 voluntary | ✗ 不支持 |

**决策**: 确认 H1，进入 L4 锁分析。

### 5.4 回溯机制

当交汇检查点发现**证据冲突**时，必须触发回溯：

```
┌─────────────────────────────────────────┐
│              回溯触发条件                │
├─────────────────────────────────────────┤
│ 1. 主假设与 Bottom-Up 证据矛盾           │
│ 2. 竞争性假设获得更强证据支持            │
│ 3. 证据不足以支持任何假设                │
└─────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────┐
│              回溯层级选择               │
├─────────────────────────────────────────┤
│ 轻微冲突: 回溯到同层的其他发散分支        │
│ 中度冲突: 回溯到上一层重新发散           │
│ 严重冲突: 回溯到 L0，重新定义问题        │
└─────────────────────────────────────────┘
```

## 6. 与现有工具的映射

### 6.1 工具在分层架构中的定位

| 工具 | 当前定位 | 方法论定位 | 层次贡献 |
|------|----------|-----------|----------|
| `check-cpu-bottleneck` | Phase 1 | L2 Resource 定界 | 确认 CPU 是否为瓶颈 |
| `show-cpu-usage` | Phase 1 | L2 Resource 分析 | 资源利用率分解 |
| `detect-anomalies` | Phase 2 | L0-L1 时序分析 | 现象层特征提取 |
| `get-process-top` | Phase 2 | L2-L3 组件识别 | 进程级资源归属 |
| `get-comm-top` | Phase 2 | L2-L3 组件识别 | 服务级聚合 |
| `cluster-symbols` | Phase 3 | L3-L4 语义聚类 | 机制层模式识别 |
| `cluster-paths` | Phase 3 | L4 调用链分析 | 代码层路径聚合 |
| `get-hotspots` | Phase 4 | L4 热点识别 | 代码层瓶颈定位 |
| `find-callers` | Phase 5 | L4 溯源分析 | 代码层根因确认 |
| `analyze-core-distribution` | Phase 3 | L2-L3 均衡性 | 调度/并行度分析 |
| `count-process-variety` | Phase 2 | L3 进程行为 | 组件层异常检测 |

### 6.2 推荐的层次化分析流程

```bash
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# L0-L1: 现象定界与主导驱动识别 (Top-Down 发散)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 维度1: 系统资源 (L2 预检查)
shecr check-cpu-bottleneck --data perf.data &
shecr show-cpu-usage --data perf.data &

# 维度2: 时序特征 (L0 分析)
shecr detect-anomalies --data perf.data &

# 维度3: 负载特征 (L1 分析 - 需外部数据)
# TODO: 需要补充负载分析工具

wait
# → CP-1-1: 确定主导驱动层

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# L2: 资源瓶颈深入 (如果 CP-1-1 确认是 CPU 主导)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 维度1: 利用率分解
shecr show-cpu-usage --data perf.data &

# 维度2: 核心分布 (均衡性)
shecr analyze-core-distribution --data perf.data &

# 维度3: 进程归属
shecr get-process-top --data perf.data &
shecr get-comm-top --data perf.data &

wait
# → CP-2-1: 确定 CPU 瓶颈模式

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# L3: 组件层分析 (如果 CP-2-1 确认是单核饱和)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 维度1: 语义聚类 (机制识别)
shecr cluster-symbols --data perf.data &

# 维度2: 进程行为
shecr cluster-comm --data perf.data &

shecr count-process-variety --data perf.data &

wait
# → CP-3-1: 确定组件级瓶颈类型

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 维度1: 热点识别
shecr get-hotspots --data perf.data --top-n 20 &

# 维度2: 调用路径
shecr cluster-paths --data perf.data --min-depth 3 &

wait

# 维度3: 针对热点溯源 (基于 Top-Down 假设)
# 如果 CP-3-1 确认是锁竞争:
shecr find-callers --target pthread_mutex_lock &

# 如果 CP-3-1 确认是调度问题:

wait
# → CP-4-1: 假设-证据交汇，确认根因
```

## 8. 总结

本文档提出的方法论核心要点：

1. **真正的 Top-Down**：从现象到代码的层次递进，每层并行发散
2. **真正的 Bottom-Up**：从样本到假设的证据聚合，严格证伪机制
3. **Hierarchical Driver**：五层驱动模型，明确问题驱动力层次
4. **交汇检查点**：强制假设-证据对比，防止过早收敛
5. **回溯机制**：证据冲突时能够回到上层重新发散

**与当前决策树的关键差异**：

| 维度 | 当前决策树 | 本文档方法论 |
|------|-----------|-------------|
| 结构 | 线性 Phase | 层次 Level |
| 发散 | 有限并行 | 每层强制发散 |
| 收敛 | 逐步深入 | 交汇检查点才允许收敛 |
| 回溯 | 无 | 显式回溯机制 |
| 验证 | 单工具验证 | 多证据交叉验证 |
