# 诊断命令设计文档

> 帮助用户快速选择合适的诊断工具

---

## 命令分类总览

perf-hunter 提供 13 个诊断命令，按分析层次分为 5 类：

| 分类 | 命令数 | 分析对象 | 典型场景 |
|------|--------|----------|----------|
| **系统资源层** | 4 | 系统/核心/进程 | 环境边界检查、负载分布 |
| **进程组层** | 2 | 进程名分组 (comm) | 多进程服务、worker pool |
| **热点识别层** | 2 | 符号/函数 | 瓶颈定位、热点溯源 |
| **模式聚类层** | 4 | 语义规则/路径/进程 | 锁竞争、调度、内存回收、进程风暴 |
| **追踪管理层** | 1 (+8子命令) | 诊断流程/问题 | 状态追踪、报告生成 |

### 命令清单速查

| 分类 | 命令 | 一句话描述 |
|------|------|------------|

| | `show-cpu-usage` | 显示CPU利用率(user/kernel) |
| | `get-process-top` | 进程CPU利用率排行 |
| | `analyze-core-distribution` | 核心级负载分布分析 |
| **进程组层** | `get-comm-top` | 进程组聚合CPU排行 |
| | `cluster-comm` | 按进程名聚类识别异常 |
| **热点识别层** | `get-hotspots` | 热点函数排行 |
| | `find-callers` | 热点函数调用链溯源 |

| | `cluster-paths` | 按调用路径前缀聚类 |
| | `detect-anomalies` | CPU利用率时序异常检测 |
| | `count-process-variety` | 短生命周期进程风暴检测 |
| **追踪管理层** | `trace` | 诊断追踪与报告管理(init/add/complete/issues/timeline/finalize/export/audit) |

## 层次化分析框架

### 三层观测模型

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                              System 层 (系统)                                │
│  观测对象: CPU/内存/IO/网络整体资源                                          │
│  工具: check-cpu-bottleneck, show-cpu-usage, detect-anomalies               │
│  问题: "系统有没有问题?"                                                      │
└───────────────────────────────┬─────────────────────────────────────────────┘
                                │ 下沉条件: 发现特定进程/进程组异常
                                ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                           Group 层 (进程组/Comm)                             │
│  观测对象: 相同进程名的进程群体 (如 nginx workers, app instances)              │
│  工具: get-comm-top, cluster-comm, count-process-variety                     │
│  问题: "哪个服务/进程组有问题?"                                               │
└───────────────────────────────┬─────────────────────────────────────────────┘
                                │ 下沉条件: 发现组内个体差异大
                                ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                         Entity 层 (进程实例/PID)                             │
│  观测对象: 特定进程实例 (如 PID 8888 这个 worker)                             │
│  工具: get-hotspots --pid, cluster-symbols --pid, find-callers --pid         │
│  问题: "具体哪个进程实例有问题?根因是什么?"                                    │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 层次间切换原则

#### 下沉触发条件 (何时深入下一层)

| 当前层 | 异常信号 | 下沉方向 | 判断方法 |
|--------|----------|----------|----------|
| **System** | `show-cpu-usage` 显示 user/sys 异常 | → **Group** | `get-process-top` / `get-comm-top` 识别异常进程组 |
| **System** | 多核不均衡但无单一进程占满 | → **Group** | `analyze-core-distribution` 显示多进程分散负载 |
| **Group** | 同 comm 进程 CPU 差异大 (如 70% vs 5%) | → **Entity** | `get-process-top` 识别特定 PID 异常 |
| **Group** | `count-process-variety` 显示进程风暴 | → **Entity** | 追踪单个进程生命周期 |
| **Entity** | `--pid` 分析发现热点 | → **代码** | `find-callers` 溯源到具体函数 |

#### 上浮触发条件 (何时返回上一层)

| 当前层 | 异常信号 | 上浮方向 | 判断方法 |
|--------|----------|----------|----------|
| **Entity** | 单个 PID 分析无异常 | → **Group** | 可能问题在进程间交互，需看整体 |
| **Entity** | 多个 PID 显示相似异常模式 | → **Group** | 升级为进程组整体问题 |
| **Group** | 所有进程组都正常 | → **System** | 问题可能在系统层 (如内核、驱动) |
| **Group** | 进程组间交互问题 (如服务间调用) | → **System** | 需全局视角看调用链 |

### 各层工具组合

#### System 层 (资源定界)

| 工具 | 用途 | 输出解读 | 下沉信号 |
|------|------|----------|----------|
| `check-cpu-bottleneck` | 系统级瓶颈 | 是否饱和/限制 | 饱和但不知谁导致 → 下沉 |
| `show-cpu-usage` | 资源分解 | user/sys/idle 比例 | sys% 高 → 检查内核模式 |
| `detect-anomalies` | 时序异常 | 尖峰/跌落时刻 | 异常时刻 → 下沉找对应进程 |

#### Group 层 (服务定位)

| 工具 | 用途 | 单体/群体 | 切换信号 |
|------|------|----------|----------|
| `get-comm-top` | 进程组资源排行 | 群体视角 | PID 差异大 → 下沉到 Entity |
| `cluster-comm` | 组级异常模式 | 群体视角 | 需要具体函数 → 下沉 |
| `count-process-variety` | 进程风暴检测 | 群体行为 | 发现风暴 → 下沉看单个进程 |

#### Entity 层 (根因定位)

| 工具 | 用途 | 必须加过滤? | 上浮信号 |
|------|------|-------------|----------|
| `get-hotspots --pid` | 特定进程热点 | **必须** `--pid` | 热点不在预期中 → 上浮 |
| `cluster-symbols --pid` | 特定进程瓶颈模式 | **必须** `--pid` | 模式与群体不一致 → 上浮 |
| `find-callers --pid` | 特定进程调用链 | **必须** `--pid` | 调用链涉及其他进程 → 上浮 |
| `cluster-paths --pid` | 特定进程执行路径 | **必须** `--pid` | 路径显示 IPC → 上浮 |

### 层次分析示例

#### 场景: 发现系统 CPU 高

```bash
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# Layer 1: System 层分析 (无过滤)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

spear check-cpu-bottleneck --data perf.data
# → 输出: SINGLE_CORE_SATURATION (单核满载)

spear show-cpu-usage --data perf.data
# → 输出: user 65%, sys 25% (用户态为主)

# 下沉判断: 系统有问题，需定位具体进程

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# Layer 2: Group 层分析 (识别进程组)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

spear get-comm-top --data perf.data
# 输出:
#   myapp  60% (kernel: 5%)   ← 异常高
#   nginx  10% (kernel: 2%)
#   ...
# → 判断: myapp 进程组有问题

# 检查组内分布
spear get-process-top --data perf.data
# 输出:
#   PID 8888 (myapp)  55%    ← 异常高
#   PID 8889 (myapp)   3%    ← 正常
#   PID 8890 (myapp)   2%    ← 正常
# → 判断: 不是整个 myapp 组问题，而是 PID 8888 个体异常

# 下沉判断: 组内个体差异大，需下沉到 Entity 层

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# Layer 3: Entity 层分析 (精确定位)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# ⭐ 必须使用 --pid 8888，不能用 --comm myapp
spear get-hotspots --pid 8888 --top-n 10
# → 发现特定热点函数 func_xyz

spear cluster-symbols --pid 8888
# → 发现 EVENT_SCHEDULER 高 (调度频繁)

spear find-callers --target schedule --pid 8888
# → 溯源到业务逻辑: process_task → yield → schedule

# 对比正常 PID 验证
spear get-hotspots --pid 8889 --top-n 10
# → 正常 PID 没有 func_xyz 热点 ✅ 确认是 PID 8888 特有问题

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 根因结论
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 
# 系统层: CPU 高，单核满载
#   ↓ 下沉
# Group 层: myapp 组资源占用高
#   ↓ 下沉 (发现个体差异)
# Entity 层: PID 8888 特定问题
# 
# 根因: PID 8888 处理了特定类型请求，导致频繁 yield
# 修复: 优化该请求类型的处理逻辑
```

### 常见层次误判陷阱

| 误判 | 表现 | 正确做法 |
|------|------|----------|
| **过早下沉** | 系统刚显示 CPU 高就直接 `--pid` 分析某进程 | 先 System 层确认整体状态，再逐步下沉 |
| **该沉不沉** | 发现某进程组 CPU 高，只用 `--comm` 分析整体 | 检查组内 PID 分布，差异大时用 `--pid` |
| **该浮不浮** | 多个 PID 都显示相似热点，仍逐个 `--pid` 分析 | 上浮到 Group 层用 `--comm` 一次分析 |
| **层次混乱** | 同时用 `--comm` 和 `--pid` 过滤 | 一次只在一个层次分析，清晰切换 |

### 层次选择速查表

| 你观察到的现象 | 推荐层次 | 关键工具 | 过滤参数 |
|---------------|----------|----------|----------|
| 整个系统响应慢 | System | `show-cpu-usage`, `check-cpu-bottleneck` | 无 |
| 某类服务(如 nginx)整体慢 | Group | `get-comm-top`, `cluster-comm` | `--comm` |
| 某个特定容器/实例慢 | Group | `get-comm-top` + 容器名 | `--comm` |
| 某 worker 明显比其他 worker 忙 | Entity | `get-hotspots`, `cluster-symbols` | `--pid` |
| 进程频繁创建销毁 | Group → Entity | `count-process-variety` → `--pid` | 先无，后 `--pid` |
| 单核满载其他空闲 | System → Group → Entity | `analyze-core-distribution` → 定位 PID | `--cpu-id` → `--pid` |
| 时序上出现尖峰 | System → Group | `detect-anomalies` → 对应进程 | `--start-time`/`--end-time` |
| 系统调用过高 | Group → Entity | `cluster-symbols` → `--pid` | `--comm` 或 `--pid` |

### 层次分析检查清单

```markdown
## 分析前检查清单

□ 1. 当前在哪个层次分析? (System/Group/Entity)
□ 2. 为什么选择这个层次? (根据什么信号下沉/上浮?)
□ 3. 过滤参数是否正确? 
   - System 层: 无过滤
   - Group 层: `--comm` 或 `--comm-regex`
   - Entity 层: `--pid`
□ 4. 如果发现异常，是否需要在相邻层验证?
   - Entity 层发现 → 对比 Group 层是否一致
   - Group 层发现 → 对比 System 层是否一致
□ 5. 分析结论与当前层次是否匹配?
   - 不要以 Entity 层结论推断 System 层状态
   - 不要以 System 层结论直接指定 Entity 层修复
```

### 工具的双向使用模式

所有工具都支持 **全局视角** 和 **单体视角** 两种模式：

| 工具 | 全局模式 (发现) | 单体模式 (验证) | 过滤参数 |
|------|----------------|----------------|----------|
| `get-hotspots` | 全系统热点排行 | 特定进程的热点分布 | `--comm`, `--pid` |
| `cluster-symbols` | 全系统瓶颈模式 | 特定进程的语义聚类 | `--comm`, `--pid` |
| `find-callers` | 全局调用溯源 | 特定进程的调用链 | `--comm`, `--pid` |
| `analyze-core-distribution` | 全系统核心分布 | 特定进程的并行度 | `--comm`, `--pid` |
| `cluster-paths` | 全系统路径聚类 | 特定进程的调用路径 | `--comm`, `--pid` |
| `detect-anomalies` | 全系统时序异常 | 特定核心的异常检测 | `--cpu-id` |

> 💡 **单体视角的两个层次**:
> - `--comm` 层次：分析**进程组**整体行为（如所有 nginx worker）
> - `--pid` 层次：分析**特定进程实例**行为（如 PID 1234 这个 worker）
> 
> 建议先用 `get-process-top` 判断是群体问题还是个体异常，再选择过滤层次

### 关键交汇检查清单

| 检查项 | Bottom-up 证据 | Top-down 预期 | 交汇标准 |
|--------|----------------|---------------|----------|
| **热点类型** | get-hotspots 显示的函数类型 | 假设路径预期的问题类型 | 类型一致 |
| **调用上下文** | find-callers 显示的调用链 | 假设路径预期的调用来源 | 来源匹配 |
| **进程分布** | get-comm-top 显示的进程占比 | 假设路径预期的影响范围 | 范围吻合 |
| **时序特征** | detect-anomalies 显示的异常时刻 | 假设路径预期的触发时机 | 时刻对齐 |
| **并行特征** | analyze-core-distribution 显示的核心分布 | 假设路径预期的并行度 | 模式一致 |

### 交汇失败的常见原因

| 失败模式 | 表现 | 解决策略 |
|----------|------|----------|
| **证据不足** | Bottom-up 发现的热点无法解释主要性能损失 | 返回 Step 1，扩大搜索范围或使用更细粒度工具 |
| **假设偏差** | Top-down 预期的路径没有对应的 Bottom-up 证据 | 提出新假设，重新走 Top-down 路径 |
| **多重问题** | 多个独立问题叠加，单一假设无法覆盖 | 分解问题，分别进行双向分析 |
| **观测盲区** | 工具无法观测到实际瓶颈 (如硬件级问题) | 引入外部观测手段 (如硬件计数器) |

```bash
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# Bottom-up 证据:
# - 热点: pthread_mutex_lock 25%
# - 模式: EVENT_LOCK_CONTENTION 40%
# - 进程: myapp 高 kernel%

# ⚠️ 关键判断: 是单个 PID 异常还是群体问题？
# 查看 get-process-top 输出:
#   PID 8888 (myapp)  70%  ← 异常高
#   PID 8889 (myapp)   5%  ← 正常
# → 结论: **特定 PID 8888 异常**，应使用 --pid 8888 分析

# 生成 Top-down 假设:
# H1: PID 8888 内部存在严重锁竞争
# H2: 特定请求导致该 worker 进入异常路径

# 交汇验证: 对比异常 PID 和正常 PID 的差异
spear get-hotspots --pid 8888 --top-n 10 > /tmp/buggy.txt
spear get-hotspots --pid 8889 --top-n 10 > /tmp/normal.txt
diff /tmp/buggy.txt /tmp/normal.txt

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# Phase 3: 单体聚焦验证 (聚焦期)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 对异常 PID 8888 进行深度分析 (而非整个 myapp)

# 3.1 聚焦热点确认 ⭐ 使用 --pid
spear get-hotspots --pid 8888 --top-n 10
# 确认: pthread_mutex_lock 在异常 PID 内是否仍然高

# 3.2 调用链溯源 ⭐ 使用 --pid
spear find-callers --target pthread_mutex_lock --pid 8888
# 得到: 该特定进程实例在哪些业务逻辑频繁加锁

# 3.3 并行度检查 ⭐ 使用 --pid
spear analyze-core-distribution --pid 8888
# 确认: 该 PID 是否被绑定到特定核心

# 3.4 语义聚类聚焦 ⭐ 使用 --pid
spear cluster-symbols --pid 8888
# 确认: 该 PID 的锁竞争占比

# 对比验证: 与正常 PID 8889 对比，确认差异
# 如果 --pid 8889 显示正常模式，则确认问题只存在于 8888
# 如果 --comm myapp 显示整体问题，则可能所有 worker 都有类似问题

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# Phase 4: 根因确认
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 交汇结论:
# - 全局视角发现锁竞争是主要问题
# - **PID 级别分析**确认问题集中在特定 worker (PID 8888)
# - 对比正常 PID (8889) 发现差异: 异常 PID 处理特定请求类型
# - 调用链溯源找到具体业务代码位置
# - 根因: **特定类型的请求**导致 PID 8888 进入高频锁竞争路径
# 
# 修复建议: 
# - 优化该请求类型的处理逻辑，减小锁粒度
# - 或考虑将该请求类型路由到其他 worker 分散负载
```

## 场景-层次映射参考

> 以下场景分析仅供参考，**不要**生搬硬套。遵循核心框架：System → Group → Entity

### 常见场景的起始层次

| 现象 | 建议起始层 | 关键初始工具 | 典型下沉路径 |
|------|-----------|-------------|-------------|
| **单进程 CPU 高** | System → 快速下沉到 Group | `get-process-top` | 发现 PID 差异 → Entity (`--pid`) |
| **系统整体缓慢** | System | `show-cpu-usage`, `cluster-symbols` | sys% 高 → 检查内核模式 → 定位进程 |
| **疑似进程风暴** | Group | `count-process-variety` | 确认风暴 → 采样 PID → Entity |
| **负载不均衡** | System | `analyze-core-distribution` | 定位核心 → 查看该核心 PID → Entity |
| **高内核态** | System | `show-cpu-usage`, `cluster-symbols` | 按模式分支 → Group/Entity |

### 场景分析核心原则

```
不要问: "这是什么场景?"
要问: "从哪一层开始分析? 何时下沉/上浮?"

所有场景都遵循统一流程:
System 层 (必做) 
    → 发现异常进程组? → Group 层
        → 组内个体差异大? → Entity 层 (PID)
        → 组内均匀? → 在 Group 层解决
    → 所有组正常? → 在 System 层找原因 (内核/驱动/硬件)
```

## 从发散到聚焦的执行节奏

### 三阶段工具使用模式

```bash
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 阶段1: 发散扫描 (全局视角，不加过滤)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 同时执行，广泛收集现象
spear check-cpu-bottleneck &
spear show-cpu-usage &
spear get-process-top &
spear get-comm-top &
spear detect-anomalies &
wait

# 发现问题迹象后，进行 Bottom-up 热点搜索
spear get-hotspots --top-n 20
spear cluster-symbols
spear cluster-paths

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 阶段2: 双向交汇 (组合使用)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 针对发现的热点/模式，进行双向验证
# 1. Bottom-up 追溯
spear find-callers --target <hotspot1>
spear find-callers --target <hotspot2>

# 2. Top-down 假设验证 (与全局结果对比)
# 如果单体过滤结果与全局模式一致，假设被证实
spear get-hotspots --comm <target>        # vs 全局 get-hotspots
spear cluster-symbols --comm <target>     # vs 全局 cluster-symbols

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 阶段3: 聚焦验证 (单体视角，加过滤)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

# 确认问题确实在特定实体
spear get-hotspots --comm <target> --top-n 10
spear find-callers --target <hot_func> --comm <target>
spear analyze-core-distribution --comm <target>
spear cluster-symbols --comm <target>
```

### 关键决策检查点

| 检查点 | 全局证据 | 单体证据 | 交汇结论 |
|--------|----------|----------|----------|
| **热点确认** | 全局 get-hotspots 显示 func_xyz 高 | `--comm X` 后 func_xyz 仍然高 | 热点确实在目标进程 |
| **模式确认** | 全局 cluster-symbols 显示锁竞争 | `--comm X` 后锁竞争仍然显著 | 锁问题确实在目标进程 |
| **调用链确认** | 全局 find-callers 显示业务调用 | `--comm X` 后调用链一致 | 调用关系确实在目标进程 |
| **并行度确认** | 全局 analyze-core-distribution 显示不均衡 | `--comm X` 后仍然不均衡 | 并行问题确实在目标进程 |

## 分析流程速查卡

### 完整分析流程 (打印贴桌边)

```
┌─────────────────────────────────────────────────────────────────┐
│  Step 1: System 层 (必做)                                        │
│  □ check-cpu-bottleneck                                         │
│  □ show-cpu-usage                                               │
│  □ detect-anomalies                                             │
│  过滤: 无                                                        │
│  输出: 系统整体状态 + 下沉信号                                    │
└───────────────────────────────┬─────────────────────────────────┘
                                │ 下沉: 发现特定进程组异常
                                ▼
┌─────────────────────────────────────────────────────────────────┐
│  Step 2: Group 层                                               │
│  □ get-comm-top    (识别异常进程组)                              │
│  □ get-process-top (检查组内 PID 分布)  ⭐ 关键                  │
│  过滤: 无 或 --comm                                              │
│  输出: 哪个 comm 异常 + 组内是否均匀                              │
└───────────────────────────────┬─────────────────────────────────┘
                │               │               │
    均匀        │               │               │ 个体差异大
    (都高)      │               │               │ (某PID特别高)
                │               │               │
                ▼               │               ▼
┌──────────────────┐            │    ┌──────────────────┐
│ 用 --comm 分析    │            │    │ 下沉到 Entity    │
│ 整体问题          │            │    │                  │
└──────────────────┘            │    └────────┬─────────┘
                                │             │
                                └─────────────┘
                                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  Step 3: Entity 层 (精确定位)                                    │
│  □ get-hotspots --pid <异常PID>                                  │
│  □ cluster-symbols --pid <异常PID>                               │
│  □ find-callers --target <热点> --pid <异常PID>                   │
│  可选: 对比正常 PID                                               │
│    □ get-hotspots --pid <正常PID>                                │
│  输出: 特定 PID 的根因                                            │
└─────────────────────────────────────────────────────────────────┘
```

### 层次选择一句话原则

| 情况 | 操作 |
|------|------|
| 刚拿到数据 | **不加任何过滤**，System 层扫描 |
| 发现某服务异常 | 用 `--comm` 在 Group 层分析 |
| 发现某实例特别慢 | 用 `--pid` 在 Entity 层分析 |
| 多个实例相似异常 | 上浮到 Group 层用 `--comm` |
| 所有服务都异常 | 上浮到 System 层检查资源 |

### 参数使用速查

```bash
# System 层 - 无过滤
spear show-cpu-usage --data perf.data

# Group 层 - --comm 过滤
spear get-hotspots --comm myapp --data perf.data

# Entity 层 - --pid 过滤 ⭐
spear get-hotspots --pid 1234 --data perf.data

# 时间维度 - 配合任意层次
spear get-hotspots --start-time "10:00" --end-time "10:05"

# 核心维度 - 配合任意层次  
spear get-hotspots --cpu-id 0
```

### 何时下沉到 PID 级别分析

#### 需要 `--pid` 的典型场景

| 场景 | 判断方法 | 分析策略 |
|------|----------|----------|
| **特定 worker 异常** | `get-process-top` 显示同名进程 CPU 差异大 | `--pid <异常PID>` 对比 `--pid <正常PID>` |
| **负载不均衡** | `analyze-core-distribution` 显示特定核心满载 | 检查该核心上具体哪个 PID 导致 |
| **进程生命周期短** | `count-process-variety` 发现短生命周期进程 | `--pid` 追踪单个实例行为 |
| **连接/请求不均** | 多进程服务中某些 worker 特别忙 | 对比忙/闲 PID 的热点差异 |

#### `--pid` vs `--comm` 选择决策

```
get-process-top 显示多个 myapp 进程
    │
    ├─► 各 PID CPU 相近 (如 10%, 12%, 11%)
    │   └── 使用 --comm myapp (群体行为分析)
    │
    └─► 某 PID 显著高 (如 80%, 5%, 3%)
        └── 使用 --pid <高CPU_PID> (个体异常分析)
            └── 必要时对比 --pid <正常PID>
```

#### PID 级别分析示例

```bash
# 1. 发现异常 PID
spear get-process-top --top-n 20
# 输出: PID 8888 (worker)  75%  ← 异常
#       PID 8889 (worker)   3%  ← 正常

# 2. 对比分析异常 vs 正常
# 热点对比
spear get-hotspots --pid 8888 --top-n 10 > /tmp/hot_8888.txt
spear get-hotspots --pid 8889 --top-n 10 > /tmp/hot_8889.txt
diff /tmp/hot_8888.txt /tmp/hot_8889.txt

# 模式对比
spear cluster-symbols --pid 8888
spear cluster-symbols --pid 8889

# 3. 对异常 PID 深度溯源
spear find-callers --target <hot_func> --pid 8888
spear cluster-paths --pid 8888
```

## 参数快速参考

### 通用参数（大多数命令支持）

| 参数 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `--data` | string | **必选** perf 数据文件路径 | `--data perf.data.txt` |
| `--freq` | int | 采样频率(Hz)，原始 perf 格式需要 | `--freq 19` |
| `--cpu-id` | int | 过滤特定 CPU | `--cpu-id 0` |
| `--pid` | int | 过滤特定进程 | `--pid 1234` |
| `--comm` | string | 过滤进程名，支持逗号分隔多值 | `--comm nginx,myapp` |
| `--comm-regex` | string | 进程名正则匹配 | `--comm-regex "app_.*"` |
| `--start-time` | string | 开始时间过滤 | `--start-time "2024-01-15T10:00:00"` |
| `--end-time` | string | 结束时间过滤 | `--end-time "2024-01-15T10:05:00"` |
| `--top-n` | int | 输出条目限制 | `--top-n 20` |

### 时间格式支持

- Unix 时间戳: `1705312800`
- ISO 8601: `2024-01-15T10:00:00+08:00`
- 日期时间: `2024-01-15 10:00:00`
- 仅日期: `2024-01-15`

## 命令输出说明

### 统一输出结构

所有诊断命令输出遵循统一格式：

```json
{
  "_risk": {
    "level": "warning",
    "message": "风险描述",
    "hint": "建议操作",
    "action_required": true
  },
  "data": { ... },
  "summary": { ... },
  "time_range": {
    "start": "2026-03-02T10:30:00+08:00",
    "end": "2026-03-02T10:35:00+08:00"
  }
}
```

### Risk 级别说明

| 级别 | 含义 | 建议动作 |
|------|------|----------|
| `none` | 无风险 | 继续分析 |
| `info` | 信息提示 | 了解即可 |
| `warning` | 潜在问题 | 建议深入分析 |
| `critical` | 严重问题 | **必须**处理并记录到 Trace |
