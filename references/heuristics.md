# SPEAR 启发式规则手册

> 本手册浓缩性能诊断的启发式规则与领域专家经验，作为 `workflow.md` 分析流程和 `tools.md` 命令参考的补充。

---

## SPEAR 方法论命名

- **S**ystematic - 从资源边界到业务代码的层级化分析
- **P**erformance - 专注高负载、低频采样场景
- **E**mpirical - 工具驱动，无证据不猜测
- **A**nalysis - 多维度关联，结合专家规则库
- **R**eflection - 自我批判机制，对抗确认偏误

---

## 五大认知闭包

### 1. 经验锚定 (Empirical Anchoring)
**原则**: 无工具数据，不进行逻辑推演  
**要求**: 每个假设必须对应一个探测动作

### 2. 竞争性假设 (Competing Hypotheses)
**原则**: 保持"双线思维"  
**示例**: 低效业务逻辑（主动）vs 调度/资源压制（被动）

### 3. 搜索空间收敛 (Search Space Convergence)
**原则**: 漏斗模型 - 先定天花板，再找主干道，最后定位局部

### 4. 因果交叉验证 (Causal Cross-Validation)
**原则**: 证据必须形成链条  
**示例**: 业务层锁竞争必须与系统层调度延迟相关联

### 5. 证伪优先 (Falsification)
**原则**: 最终结论前审计证据链  
**问题**: "问题解决了吗？还有其他可能性吗？"

## 领域诊断规则

### 进程级诊断标准

| 规则 | 描述 | 优先级 |
|------|------|--------|
| 资源边界压制 | 优先分析 Cgroup 规格和限流指标 | **#1** |
| 全路径审计 | 使用 inclusive 统计确保稳定，忽略单点噪声 | 高 |
| 基础库聚合 | 识别公共工具函数（memcpy, malloc）- 指示数据处理模式问题 | 中 |
| 用户空间同步损耗 | 监控同步原语比例以发现锁竞争 | 中 |
| 进程生命周期异常 | 高 PID 多样性 + 低单 PID 样本数 = 进程风暴 | 高 |

### 系统级诊断标准

| 规则 | 描述 | 指标 |
|------|------|------|
| 中断与调度延迟 | 内核长临界区 | `spin_unlock_irqrestore` 模式 |
| 内核全局聚合 | 跨进程内核开销聚合 | 所有参与者均受影响 |
| 调度器效率 | 调度器内部函数开销 | >10% 表示系统过载 |
| 架构与内存瓶颈 | 内存直接回收和 TLB 同步 | 微突发抖动检测 |

### 问题边界判定规则

**核心原则**: 通过行为相似性和依赖路径判断问题边界

| 判定维度 | 系统问题 | 单体问题 |
|----------|----------|----------|
| **行为相似性** | 多个进程表现出相似的症状（高CPU、相同热点函数、异常调用模式） | 单个进程或特定进程独有的异常行为 |
| **共同依赖路径** | 问题出现在共享的依赖路径上（内核、共享库、基础设施服务） | 问题局限于进程自身的代码路径 |
| **影响范围** | 跨进程、跨用户、或全局性的性能下降 | 仅限于特定进程实例或其直接子进程 |

**判定逻辑**:
```
IF (多个进程表现出相似症状) AND (共享共同依赖路径):
    → 系统问题（基础设施/平台层问题）
ELSE IF (症状局限于单个进程) OR (无共同依赖路径):
    → 单体问题（应用层问题）
```

**典型场景对照**:

| 场景 | 判定 | 依据 |
|------|------|------|
| 多个 MySQL 连接进程都在等待同一把内核锁 | 系统问题 | 共同依赖：内核锁路径 |
| 某业务进程热点在其独有的业务逻辑函数 | 单体问题 | 无共同依赖：进程私有代码 |
| 所有进程 `__libc_start_main` 开销异常高 | 系统问题 | 共同依赖：glibc 初始化路径 |
| 不同业务进程均出现 `page_fault` 延迟 | 系统问题 | 共同依赖：内存子系统 |
| 单个 Java 进程的 GC 线程 CPU 过高 | 单体问题 | 无共同依赖：进程内部 GC 行为 |

### 样本丢失（丢点）评估规则

**核心原则**: 样本丢失本身是**系统问题**的指示器

| 评估维度 | 说明 |
|----------|------|
| **丢点本质** | perf 采样依赖于中断，若中断被抑制（关中断、高优先级中断抢占、NMI），则产生丢点 |
| **责任归属** | 丢点是系统层面的采样基础设施失效，反映系统在高负载下的观测能力受限 |
| **关联症状** | 通常伴随：高内核态 CPU、调度延迟、硬中断/软中断堆积 |

**判定逻辑**:
```
IF (检测到样本丢失) OR (实际样本数 << 预期样本数):
    → 系统问题（内核/硬件层压力过高，导致采样中断被抑制）
```

**注意**: 丢点本身不指示业务问题边界，而是提示系统层面的观测限制。在丢点严重的场景下，任何基于采样的分析结论都应标记为"存在观测盲区"。

**检测方法**:
- 对比 `perf record` 报告中的 `sampled` vs `lost` 计数
- 评估实际采集样本数是否匹配预期（基于 CPU 利用率和采样时长估算）
- 结合 `assess_sample_reliability()` 输出的 `CRITICAL` 等级判断是否可能丢点

## 工具使用铁律

1. **工具强制**: 禁止"裸猜测"。每次分析必须以"根据工具检测结果..."开始
2. **范围严谨**: 禁止从阶段 1 跳到阶段 4。严格遵循环境→代码路径
3. **可靠性阈值**: 19Hz 采样时验证样本总数，低于置信阈值标记为"推测"
4. **证伪优先**: 优先收集排除搜索域的证据，而非支持假设的证据
